# Arrify listening prototype

Native SwiftUI iPhone/iPad app, iOS 18+, in the Arrify repository. `ArrifyCore`
contains Sendable API DTOs, HTTPS transport, rotating session handling and playback
intent policy. The app owns one main-actor AVPlayer coordinator, independently of
view lifetimes. No third-party Swift dependencies.

## Build and test

Open `Arrify.xcodeproj`, scheme `Arrify`. CI uses Xcode 26.5 on the macOS 26 runner;
recorded compiler/SDK versions and artifacts accompany every qualification run.

```
cd ios
swift test
xcodebuild -project Arrify.xcodeproj -scheme Arrify \
  -destination 'generic/platform=iOS' CODE_SIGNING_ALLOWED=NO build
```

The checked-in project is generated by `python3 ios/tools/generate_project.py`.
Regenerate after adding an app source file. The package is discovered by SwiftPM.
The iOS CI runs contract/policy tests, an unsigned physical-device build and iPhone
simulator UI tests, plus hosted regressions for off-main system artwork requests
and restoring an owned session without activating playback. Debug-only UI fixtures never enter Release/TestFlight builds.

## Prototype scope

- Explicit HTTPS server enrollment; Keychain token storage; single-flight rotation.
- Songs, albums and artists with paginated browsing/search and visible refresh results.
- Curated/personal playlists, account-specific channels, and website mood groupings.
- Detail pages with full server-side collection playback and shuffle; channel rotation stays on the server.
- Embedded player-item title, artist, album and cover data for supported AirPlay receivers.
- Persistent mini-player, Now Playing, seeking, previous/next, native AirPlay picker.
- AVAudioSession playback/background audio, Now Playing metadata and remote commands.
- Server-owned queue and explicit Play Here takeover; no launch-time autoplay.
- Phone-interruption consent and headphone-disconnection pause handling.
- Original/AAC/MP3 selection for the next prepared track, bounded preparation retries.

This is a **device-testing prototype**, not a complete replacement for the web app.
Requests, playlist editing/community sharing, favorites, native offline storage,
seamless endpoint switching and queue editing are subsequent milestones.
Only the loaded search-result suffix (up to 1,000 songs) becomes the initial queue.
Streaming uses the server's current + next two preparation contract; it does not
claim that audio has been downloaded onto the device.

Home and public addresses are separate explicit enrollments. Home never falls back
to the public server silently. TLS validation stays enabled; no ATS exceptions.
Control requests reject redirects. Media URLs are same-origin scoped grants; never
log them. Passwords are transient; bearer/refresh tokens live in Keychain with
AfterFirstUnlockThisDeviceOnly protection. Sign-out clears local credentials even
if revocation cannot reach the server; revoke that session separately when online.

## Physical-device acceptance

Record build, device/OS, endpoint, route, track IDs and outcome without credentials.

1. Fresh sign-in on public and home HTTPS; refresh beyond 15 minutes; sign-out/revoke.
2. Select a song, seek, pause/resume, previous/next; let two tracks end naturally.
3. Lock for two song transitions; switch apps; use lock-screen play/pause/seek/skip.
4. Interrupt with a call/Siri. Resume only with system consent; explicitly pause during
   the call and verify it remains paused afterward. Disconnect headphones.
5. Test speaker AirPlay and Apple TV separately, including next-track transition.
6. Start playback in the web app, then use Play Here. Old output must stop; reverse it.
7. Lose network during preparation/playback, restore it, retry. No silent home-to-VPS fallback.
8. Test Original, AAC and MP3, large tracks and missing source files. No silent quality downgrade.
9. VoiceOver, large Dynamic Type, iPad landscape/split view and keyboard search.
10. Pause in wired CarPlay, unplug, then explicitly resume on AirPlay and the iPhone
    speaker. No force-quit should be needed. A failed session activation should show
    an actionable error; disconnect alone must not start playback on the speaker.
11. Capture startup time, transition delays, stalls, and memory over a 30-minute session.

Simulator success does not qualify hardware AirPlay, calls or locked-device playback.

## Library iteration (0.2)

The app consumes `native_library_v1` from the same server as the web app. Deploy the
additive server endpoints before distributing this build. Refresh reloads the server
catalog; it does not trigger a media scan or download. Detail pages are bounded to
50 songs, with revision checks; Play/Shuffle resolve the whole context server-side,
with personal playlist authorization and channel rotation preserved. Song-search
row playback still uses the loaded result suffix.

Artwork thumbnails are downsampled and held in a bounded 24 MB memory cache that
clears on sign-out. Receiver artwork is embedded as JPEG bytes; receivers do not
need Arrify bearer credentials to display it. Apple TV display behavior must be
confirmed on hardware. Missing artwork clears the prior song's receiver metadata.

Native heartbeat sequence numbers persist across relaunches, with an epoch-millisecond
floor for upgrades from early builds. Output reports include the actual audio route
so admin activity remains visible after app restarts. HTTP transfers and ongoing
buffered playback remain separate measurements.

0.2.1 uses the system tab-bar bottom accessory on iOS 26+ to reserve scroll space
for the mini-player, and web-style monochrome channel art. Now Playing exposes
shuffle-upcoming and repeat Off/All/One, gated by server queue policy.
AVPlayer external item playback is disabled for this audio-only app; AVAudioSession
continues routing audio over AirPlay with Now Playing artwork. This avoids the
video-style receiver path; physical Apple TV full-screen presentation needs testing.
Uploads are now eligible for both internal and external TestFlight groups. External
availability requires beta review, review contact/login details, and group assignment;
uploading alone does not make a build externally available.

### Remote Lock Screen status

The optional WidgetKit/ActivityKit extension displays another device's playback
from the same signed-in account. The user explicitly starts it in the expanded
player. It is read-only: tapping opens Arrify, without issuing a playback command.
It does not broaden account permissions or claim that Wi-Fi membership proves
control authorization. Local-only interactive controls require a separately
verified device-pairing design before being added.

The server accepts ActivityKit update tokens through the authenticated
`/api/v1/native/live-activity` endpoint. Subscriptions are tied to the native
session family, limited to four per account, and expire after seven hours.
Revocation cascades to subscriptions. Updates are coalesced; unchanged playback
refreshes at most once a minute, with low APNs priority and a 90-second stale date.
The card ends when playback moves to another owner or the playing device goes
silent for two minutes. No silent audio or persistent background SSE is used.

Server provisioning (private data mount; never commit these files):

- `/data/secrets/apns.p8`: APNs EC private key, readable only by the runtime owner.
- `/data/secrets/apns.json`: `team_id`, `key_id`, `environment` (`production` for
  TestFlight, `sandbox` for development). The topic is fixed to
  `com.robnets.arrify.push-type.liveactivity`.
- Enable Push Notifications for the main app identifier. The widget identifier is
  `com.robnets.arrify.liveactivity`; Xcode automatic signing provisions it.

`Prepare encrypted APNs configuration` accepts `APNS_KEY_ID` and
`APNS_PRIVATE_KEY` Actions secrets and creates only a CMS-encrypted artifact for
an operator-held recipient key. The checked-in recipient certificate is public;
the matching private key is kept outside the repository. Rotate that certificate
before using the transfer after its expiry. The server needs outbound HTTPS to
APNs, curl with HTTP/2, and OpenSSL. Missing configuration leaves the feature
unavailable without affecting audio playback.

Artwork assets: the app icon is the owner's supplied image. The transparent
`web/assets/arrify-logo.png` was extracted with the built-in image-generation tool
using: “Remove only the white background including inner openings; preserve the
metallic A/music note, gold cutlass, lighting, proportions and details; true alpha
PNG, no redesign or text.” `tools/generate_brand.py` exports deterministic icon
sizes from `web/assets/arrify-icon-source.jpg`. Server custom icons remain in the
server's private data mount and do not alter another server's branding.

## Selected output naming investigation (2026-11-10)

Status: implemented conservative name handling and opt-in raw diagnostics; physical
AirPlay/Bluetooth verification is **pending**, not a claimed fix for generic OS names.
This workspace is Linux, has no attached iOS device, and its Apple CI uses simulators.
A nearby receiver or the macOS music-recognition VM cannot provide the iPhone's
AVAudioSession route values. The user's earlier screenshots establish the visible
symptom, not the raw API values.

### Code findings and changes

- Before this change, `SystemPlaybackAudioSession.outputName` already read **every
  currentRoute.outputs portName**, not portType as the destination name. Type only
  supplied an AirPlay/CarPlay prefix. A single raw `AirPlay` remained `AirPlay`.
- The session already uses `.playback`, `.default`, `.longFormAudio`, with no category
  options. This is Apple's documented long-form AirPlay configuration. AVQueuePlayer
  routes audio through that session; `allowsExternalPlayback` remains false to avoid
  changing receiver behavior to external video playback. Neither policy nor engine is
  changed just to obtain a name. Hardware A/B comparisons of these settings remain
  unperformed; documentation does not promise that changing them reveals names.
- Preserve complete selected port names locally; remove the old 80-character local
  truncation and transport-prefix insertion/removal. Port type is only a fallback for
  an empty name. Distinct selected ports are retained even if their names match.
- Refresh after route-change notifications, picker dismissal, foreground entry and
  explicit activation, immediately and at 0.6, 2 and 5 seconds. Existing reconciliation
  also refreshes. A newer event cancels old delayed reads. Never keep an old receiver's
  name when the current route becomes generic. No additional continuous timer,
  discovery, session activation, volume mutation or playback command is used for names.
- Remote-owner labels still come from the playing device's server heartbeat, not this
  controller's local route. The server's pre-existing 80-character heartbeat-output
  limit remains; it is separate from the local selected-output label.

### Public API investigation

| API | Selected destination information | Decision |
| --- | --- | --- |
| AVAudioSession.currentRoute.outputs | Selected output ports; portName, portType, uid, channels, selectedDataSource | Authoritative public iOS input for labels; capture raw values, preserve names as returned. |
| AVAudioSession.outputDataSource / selectedDataSource.dataSourceName | Selected source within a port; session outputDataSource documented for certain USB accessories | Log it, but do not mislabel a microphone/source/channel as a receiver. |
| AVPlayer.isExternalPlaybackActive | Boolean for **external video** playback | Log alongside allowsExternalPlayback; false does not mean session-based AirPlay audio is inactive. No destination-name property documented on iOS AVPlayer. |
| AVPlayer.audioOutputDeviceUniqueID | Core Audio output device ID | **macOS-only**; not an iOS alternative. |
| AVRoutePickerView / delegate | System-owned receiver UI; will-begin/did-end presentation callbacks | Keep native picker. No selected-name/list callback. Its player property is macOS-only. Do not scrape internal views or accessibility strings. |
| MPVolumeView.isWirelessRouteActive | Wireless-route Boolean (deprecated but public) | Diagnostic only; not a name or selected-member list. Preserve native volume control. |
| AVRouteDetector | Whether multiple routes are **available** | Not selected-route identity or group membership; do not enable discovery for this task. |
| AVRoutingPlaybackArbiter / participant | Which app player gets priority on constrained routes | Not speaker identity. |
| AVCustomRoutingController / AVCustomDeviceRoute | App-integrated custom protocol routes, authorization and endpoints | Not a getter for system-selected AirPlay speakers. No custom protocol added. |
| prepareRouteSelectionForPlayback | Local/external/none classification for long-form video | Not a name; avoid a route-selection operation purely for diagnostics. |

The native route picker can display system-managed receiver information without
exporting that information to its host application. Its documented delegate contract
contains presentation events, not selection details. The visible picker is therefore
not evidence of an equivalent public name getter. We cannot establish how Apple Music,
Spotify, Tidal or Sonos obtain their labels from screenshots; proprietary protocols or
Apple-only facilities must not be assumed equivalent to Arrify's AVAudioSession path.

For grouped AirPlay 2: if iOS returns multiple selected ports or a human-readable group
name, display exactly those returned names. If it returns one generic `AirPlay` port,
no reviewed public iOS API exposes the individual selected group members. Do not infer
member count from output-port count, available receivers, channel count, UID text or
saved names. Keep the honest `AirPlay` fallback and the native picker. This is the
public API boundary found in this investigation, not a fabricated hardware result.
Private AVOutputContext/MediaRemote access, KVC selectors, Bonjour-to-UID matching and
internal route-picker view traversal are intentionally excluded.

### Hardware capture procedure and evidence still needed

In Settings → Audio → Audio output diagnostics, start capture before selecting the
receiver. Capture is local, bounded to 120 records/10 minutes, cleared on sign-out or
Clear capture, and shared only explicitly. Reports contain raw names/UIDs, so do not
publish an unredacted report in the public repository. No credentials, media URLs,
server address, track details or audio are collected.

The report includes session category/mode/options/policy, all current output port
names/types/UIDs, selected source and channel fields, previous route and change reason,
AVPlayer external-playback flags, MPVolumeView wireless-active flag, local label,
displayed label, remote-owner indicator, trigger and timestamp. No fake values are
substituted for unavailable API results. JSON optional fields are absent when nil.

Run on an actual iPhone and, if available, iPad:

1. Built-in speaker → one Apple TV, Sonos or Samsung AirPlay receiver. Note the exact
   picker-selected name, capture immediately and after 5 seconds, then stop/start music.
2. Add a second AirPlay receiver to the selected group; remove the first; change the
   group again while music continues. Compare picker membership with raw outputs.
3. Bluetooth speaker/headphones: select, rename in system settings if convenient,
   reconnect, and confirm portName rather than profile/type is displayed.
4. Return to built-in audio, lock/unlock, foreground the app, and confirm no stale name.
5. From another logged-in Arrify device, observe the playing owner's reported label;
   do not confuse the observing device's local audio route with the remote owner.
6. Record receiver model/firmware, OS/build, the exact selected picker names and whether
   playback remained uninterrupted. Share the diagnostic report privately.

All of these hardware rows are currently **not run**. Simulator and formatter tests
validate code and fallback behavior, not AirPlay receiver names. Policy/engine A/B
experiments must be an isolated diagnostic run on hardware (including default vs
longFormAudio and external video allowed vs disabled), not an unverified production
playback change. They are not required or claimed as a solution by the current code.

### iPad library and remote Lock Screen controls

The iPad shell uses a fixed sidebar and an always-visible search header, outside the scrolling navigation content. It keeps the tablet player when the keyboard opens. Home contains account-scoped recent albums (daily suggestions when history is empty) and playable mood collections. Native playlist creation and adding songs use the same `Playlists` ownership rules/storage as the web. Inline unlikes keep their row until an explicit refresh, allowing immediate re-addition.

Remote Lock Screen controls start automatically while Arrify is foregrounded and another device on the **same account and locally reachable Wi-Fi/Ethernet network** owns playback. There is no Show on Lock Screen link. A Settings toggle disables automatic controls. A Live Activity uses public App Intents for previous, pause/resume, and next; it does not play silent audio or activate a local audio session. iOS decides presentation and may require device authentication for interactive buttons. This is distinct from the system Now Playing controls on the device that actually plays audio.

Automatic local verification (no household names, IP ranges, or router setup):

- The native session that acquires playback is bound to its owner/epoch on the server. Only that session may publish a rotating in-memory key and opaque Bonjour service identifier. Existing playback acquired before this upgrade needs an explicit Play here once to establish the binding.
- The controller receives an account/session/owner/epoch/command-scoped 12-second server nonce, discovers the matching `_arrify-local._tcp` service, and asks the player to authenticate that nonce with HMAC-SHA256. Keys and account/media details are never advertised. Public-IP equality and client-reported private subnets are never authorization evidence.
- Every Lock Screen command obtains a fresh, single-use proof. Replay, expired challenges, a different account/session/owner/epoch/command, or rotated keys are rejected. Keys expire after 35 seconds unless refreshed by the native player. Listener connections and challenge counts are bounded.
- Network.framework uses Wi-Fi/Ethernet and disables peer-to-peer discovery; cellular, loopback, and other interfaces are prohibited. A network-path change resets the listener/key. Ordinary playback and existing in-app/web controls retain their behavior. The old CIDR/proxy environment settings are unused.
- This verifies local reachability, not a geographical household. Network administrators can bridge/relay Bonjour or route between local networks; this does not promise resistance to deliberate relaying by someone already authenticated to the account.
- iOS asks for Local Network permission. Denial, guest-Wi-Fi isolation, unavailable multicast, or a suspended player listener makes verification unavailable; a command fails without changing playback. No silent audio or artificial background keepalive is used. Paused/background behavior and locked-device intent execution require physical-device testing.
- The initial native-to-native implementation does **not** advertise browser players. Web-to-native remote control remains available in the app, but browser-owned playback does not qualify for this automatic Lock Screen path. Passive APNs metadata can remain visible after a controller leaves; each interactive command still requires fresh local proof. Immediate removal of a suspended device's card on network change is not guaranteed by iOS.

Live Activities still require enabled iOS Live Activities and valid push provisioning. Settings now retains the ActivityKit error domain/code instead of the former generic start failure. Physical-device APNs delivery, Lock Screen presentation and same-LAN behavior require TestFlight validation; simulator compilation is not hardware verification.

Apple references: [interactive widgets and Live Activities](https://developer.apple.com/documentation/widgetkit/adding-interactivity-to-widgets-and-live-activities), [Activity authorization errors](https://developer.apple.com/documentation/activitykit/activityauthorizationerror).

Distribution qualification explicitly preserves the requested push capability before cloud signing, then verifies `aps-environment=production` in both the exported IPA and its provisioning profile before uploading that exact IPA. The old unsigned-archive/direct-upload flow did not verify this capability. This addresses a suspected provisioning cause of the generic ActivityKit start failure, but the actual device error still needs confirmation.

### Home and public server addresses

Sign-in and Settings → Connection → Server addresses accept a public HTTPS address and an optional home HTTPS address. The public origin enrolls the server's stable P-256 public key; existing credentials enroll from their already-trusted origin without extending token expiry. Before credentials or media grants go to an alternate origin, it must answer a fresh nonce with a valid signature from that pinned key and the same server ID. TLS certificates remain mandatory and redirects are rejected. Legacy servers without proof support remain public-only.

Verified home is preferred, with public fallback and a short probe cache/backoff. Network and foreground changes invalidate the probe cache. GET requests can retry once on a different verified origin; mutations and rotating refresh requests are never replayed after ambiguous transport failure. A failed/stalled remote media item can recover through the alternate verified origin at its saved position without advancing the queue. Healthy media is not restarted solely because a home route becomes available.

Small house/globe badges describe this device's **server connection**, not its AirPlay speaker or the location of a different player. Green indicates a verified connection; unavailable connections are gray. The addresses and key pin stay in Keychain credentials. Changing addresses verifies the public address belongs to the existing server. The signing private key lives in the server data volume's `secrets/server-identity.pem` (0600); retain it with private server backups. Demo and production maintain independent identities.

Real-device checks still required: home Wi-Fi → cellular and back during playback, VPN/local DNS, grouped AirPlay while changing networks, unreachable/mismatched home endpoint, and relaunch while public Internet is unavailable. No physical network-handoff test is claimed by CI.

### Remote Lock Screen artwork and volume alignment

Remote Live Activity state now includes a bounded inline JPEG thumbnail, rendered in the card instead of a permanent music-note icon. The app prepares the initial cover; server push updates carry the current cover when the app is suspended. No widget network request or public artwork URL is needed. Encoded covers stay below 2 KB and the server drops artwork if metadata would exceed its reserved payload budget. Missing artwork leaves a placeholder and never blocks transport controls. This is a cover inside the remote-control Live Activity, not Apple's full-screen local Now Playing presentation.

The volume view overrides the public `volumeSliderRect(forBounds:)` layout hook to center its track within the 44-point control frame. MediaPlayer still owns volume values and receiver synchronization. Physical AirPlay volume behavior and Lock Screen APNs artwork must be validated in TestFlight.

## Focused playback reliability release

Current-item recovery is separate from queue advancement. AVPlayer state changes
and an eight-second no-progress watchdog detect failure even when media-time
callbacks stop. A transient stall may recover naturally. Recovery has one
30-second budget: prefer a completed, size-checked cache entry; otherwise refresh
media authorization and retry, then try the verified alternate server origin.
The replacement must become ready and finish seeking before playback resumes.
Preparation and recovery hold finite system background tasks, ending on success,
cancellation, expiry or their 30-second deadline; no silent audio keeps the app alive.
Fifteen seconds of advancing audio is required before another automatic recovery
cycle is permitted. Explicit Retry starts a new bounded cycle.

Recovery retains the current track, owner epoch and play identity. Pause is local
and immediate even during a server command. Control changes, interruptions,
logout, ownership changes and track changes invalidate pending recovery. Late
responses cannot replace the new owner's player. Failed recovery reports `failed`,
not indefinite buffering; `recovering` and `failed` freeze server cursor projection
without altering user intent or adding duplicate history. Audio-service resets
recreate AVQueuePlayer and require user action. No proximity-to-end heuristic skips
an unfinished song. The existing server-confirmed next-item gate remains in place,
and automatic transition retries reuse their transition identifier.

Opt-in diagnostics record fixed playback/waiting states, sanitized error domains
and numeric error codes, cache use, attempts and exhaustion. They never include
media URLs, credentials, exception descriptions or audio. Read-ahead downloads
current audio first and queues future local files instead of opening duplicate
remote player items. Cache files that disappear, change size or fail preparation
are invalidated. This is not a promise of full decode integrity or offline rights.

Home refreshes account-scoped recent songs after acknowledged actual playback and
on foreground entry. Home features saved and curated Playlists; Moods remains
available in Library. On iPhone, connection and playback status sit beside the
mini-player rather than over the navigation search field, so failure messages
cannot block a new search.

Validation includes real AVQueuePlayer tests using generated local audio, delayed
server responses, failed preparation, cached replacement at a saved position,
user Pause during a pending transition, ownership changes, interruption handling,
media-service resets, near-end stalls, history acknowledgement and damaged cache.
Server tests cover history deduplication and position/ownership invariants for new
observations. Real-device AirPlay/CarPlay, calls, Wi-Fi/cellular changes and extended
listening remain required field verification: simulator tests cannot certify those
routes. Record outcomes with build number and opt-in diagnostics; do not describe
unperformed hardware checks as passed.

### Separate design: offline queue continuity (not implemented)

Keep server acknowledgement mandatory in this release. A later offline design
would need a server-issued bounded reservation naming the account/session, owner
epoch, exact ordered play identities, media revisions and expiry. It needs an
explicit maximum disconnected interval and takeover/revocation policy, followed by
idempotent reconciliation of completed transitions. Cached bytes alone confer no
new authority. No implementation should infer permission from Wi-Fi, weaken grant
validation, silently take ownership back, or replay old songs after reconnecting.
Codec/quality fallback also remains explicit until diagnostics establish a need;
this release does not silently downgrade original audio.
