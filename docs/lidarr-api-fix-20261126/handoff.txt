Behavior and bounds
Follow-up review fixed the per-call full inventory deserialization: read_ids now
selects only input IDs from inventory and requests in parameterized SQL IN batches
of at most 500 IDs, supporting inputs over the older 999-variable SQLite limit.
Inventory uses its existing composite (kind,id) primary-key index without casts.
Request rows override inventory mappings as before. No new DB index or schema
change was introduced; requests.lidarr_id is not indexed in the current schema,
so SQLite may still scan that smaller table, but only matching rows reach Python.

Batch reads remain 50 numeric IDs. A batch 500 falls back to singleton reads;
only singleton 404 proves deletion. A known release group is then queried using
album?foreignAlbumId=<rg>. Its exact identity is validated. Returned replacements
are used in memory, with aliases stored in the existing cache table. No schema
migration or direct UPDATE/DELETE of requests, transfers, inventory or history.
Existing downstream acquisition transitions remain unchanged and may naturally
record the current album ID when they next update a request.

Confirmed missing groups are skipped, preserving their state and reservations;
they are NOT automatically re-added or re-prepared. This deliberately leaves
truly deleted prepared requests for later operator review rather than creating
new acquisitions or changing budgets. Cache entries persist across processes
and retain the old-ID tombstone. After 3600 seconds, known groups are checked by
foreignAlbumId, never by the deleted numeric ID. New numeric IDs and groups
return normally. Unknown groups use singleton rechecks after expiry. No-Store
adapters have instance-local cache only; deployed callers use the shared Store.
Cache keys are namespaced by configured Lidarr endpoint. Changing that endpoint
causes one new validation cycle. This does not seed the 24 supplied IDs: first
encounter can still generate one batch 500 and one singleton 404 per stale ID.

For N unique pending IDs: healthy reads cost ceil(N/50) API calls. A failed batch
of k IDs costs at most 1+2k calls (one batch, k singleton reads, <=k RG lookups).
All 50 known-deleted IDs: 101 calls initially, zero while cached. Mixed two-ID
valid/deleted case: 4 initially, 1 on later passes. Unrelated singleton 500 aborts
immediately; an all-endpoints-500 outage uses 2 calls and records no deletion.
The bound is API calls; 429/502/503/504/connectivity retain four transport attempts.
Album HTTP 500 responses are not retried at transport. The live api-metadata.py
already suppressed batch-500 retries; repository API did not. Other GET retry
behavior is preserved. Unscoped track/trackfile reads are rejected before IO.
The deployed optional metadata_transport hook is preserved; older images without
that module retain the repository's original HTTP behavior.
